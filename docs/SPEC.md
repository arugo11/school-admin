# SPEC.md

## 1. 文書の目的

本書は, 学習塾向けデモシステム「生徒別学習コンパス」の実装仕様書である.
対象は, 小中学生向け進学塾の数学学習支援であり, 教室に入った生徒が iPad から答案やノートを撮影すると, システムが弱点分析と宿題候補を返し, 最後に講師が承認して確定する MVP を構築する.

本書の主目的は次の2点である.

1. Codex が自律的に実装, 評価, 修正のループを回せるように, 要件, 制約, 成功条件, 評価方法を明文化すること.
2. ハッカソン審査基準である 現場価値, 技術実装, デモ体験, 発展性 に対して, 一貫したストーリーを維持したまま短期間でデモ完成度を高めること.

## 2. 背景と狙い

塾講師は授業前の短い準備時間で, 全体授業の準備まではできても, 生徒一人ひとりの答案や宿題状況を分析し, 個別最適な宿題を設計する時間を確保しにくい. 教室長が全員分を追うのも難しい. その結果, 点数は記録されても, 誤答パターン, 解き直しの質, 途中式の崩れ, 宿題の重さの適正といった実務上重要な情報は埋もれやすい.

本システムは, 紙の答案やノートという現実世界の情報をカメラで取り込み, 教師の判断を置き換えるのではなく, 教師の準備時間を圧縮し, 個別最適の叩き台をすぐ出すことを狙う.

## 3. ハッカソン適合方針

本作品は次の審査観点に合わせて設計する.

- 現場価値: 教室という個人情報と時間制約の厳しい現場で, 生徒分析の初動を高速化する.
- 技術実装: 紙の答案というフィジカル入力をカメラで取り込み, OCR と LLM を接続する.
- デモ体験: 「答案を撮るだけで, 今夜やるべき宿題が出る」という瞬間を主役にする.
- 発展性: 塾から学校, 自習室, 学習支援教室へ拡張できる設計にする.

展示会では Wi-Fi と AC 電源は利用可能で, 一次選考は書類と展示, 最終選考は5分ピッチである. そのため, 展示で10秒以内に価値が伝わり, 5分ピッチで課題, 解決, デモ, 発展性が通る構成を前提とする.

## 4. 実装スコープ

### 4.1 MVP スコープ

今回の MVP は次を必須とする.

- 生徒一覧の表示
- iPad Safari からの答案画像アップロード
- Azure Vision Read OCR による文字抽出
- OCR 結果の正規化, 構造化
- Azure OpenAI を用いた弱点分析
- 教材カタログからの問題番号レベル宿題提案
- 講師承認 UI
- 最低限のエラー処理
- デモ用架空データ 6人分

### 4.2 今回やらないこと

今回は次を明示的にスコープ外とする.

- 面談音声入力
- 保護者向けレポート自動送信
- 長期学習履歴の高度分析
- 完全ローカル推論本番運用
- GPU VM を前提にした open weight model 実運用
- 高度な数式意味解析のみでの自動採点
- 学習コンテンツ自動生成の本格実装

### 4.3 デモで必ず見せること

- 生徒が iPad で答案を撮る
- ローカル UI に OCR プレビューが表示される
- システムが 弱点単元, 誤答パターン, 宿題の重さ を出す
- 問題番号レベルの宿題候補が提示される
- 講師が承認して宿題が確定する

## 5. 非スコープだが将来の差し替え可能性として保持する要件

設計上は次を将来的な差し替え点として意識する.

- OCR を Azure Vision API から OCR コンテナまたは別ローカル OCR に切り替える
- LLM 推論を Azure OpenAI からローカル小型モデルへ切り替える
- 教材 DB を demo 用の静的 JSON から本格的な教材管理 DB に切り替える
- 成績履歴や面談履歴の継続蓄積を追加する

## 6. 事前調査から確定している前提

以下は調査で確認できた前提であり, 実装はこれに沿う.

- 既定 subscription は Azure for Students で有効状態である.
- 既存の Azure OpenAI リソース `sitcopilotaoai23088` と deployment `sit-copilot-demo-chat` は利用可能で, `gpt-4o-mini` の API 実呼び出し成功が確認されている.
- エンドポイントは resource 固有 FQDN ではなく, `https://japaneast.api.cognitive.microsoft.com/` を使う構成である.
- `school-admin-precheck-rg` と `schooladminocr23088` `ComputerVision F0` が作成済みであり, Read OCR の最小疎通に成功している.
- Azure ML workspace / Foundry hub / project は CLI 上で見つかっておらず, `Microsoft.MachineLearningServices` と `Microsoft.SaaS` は NotRegistered である. Foundry や Marketplace 前提の構成は高リスクである.
- 日本語手書き数学答案への OCR 精度は未検証であり, そこは実装後に必ず評価が必要である.

## 7. システムの基本方針

### 7.1 アーキテクチャ方針

本番デモでは, 現実的で落ちにくい構成を優先する.

```text
iPad Safari
  -> 教室内ローカル Web アプリ
  -> ローカル API サーバー
  -> Azure Vision Read OCR
  -> OCR 正規化 / 構造化
  -> Azure OpenAI gpt-4o-mini
  -> ローカル UI へ結果返却
  -> 講師承認
```

この構成は, 既存 AOAI と作成済み Vision を再利用でき, GPU VM も不要で, デモ成功率が高い. また, UI と制御境界をローカル側に残すことで, 将来的な edge 化の説明も可能である.

### 7.2 実装優先順位

1. まず確実に動く happy path を作る.
2. 次に評価用データで弱い箇所を特定する.
3. その後に, 誤り吸収 UI, 前処理, プロンプト改善を行う.
4. 最後にデモ演出と体験品質を高める.

## 8. ユーザーとユースケース

### 8.1 主ユーザー

- 主ユーザー: バイト講師, 教室長
- 価値受益者: 生徒, 保護者

### 8.2 主要ユースケース

#### UC-01. 生徒が答案を撮影してアップロードする

- 生徒は教室の iPad で Web アプリを開く
- 生徒を選択する, もしくは仮IDで開始する
- 答案または宿題ノートの写真を撮影する
- ローカル API に送信する

#### UC-02. 講師が OCR プレビューを確認する

- システムは OCR 結果をプレビュー表示する
- 問題番号, 読み取り結果, 不確実箇所を可視化する
- 講師は必要なら軽微な修正を行う

#### UC-03. システムが弱点分析と宿題提案を返す

- システムは OCR 結果と生徒プロファイルを元に分析を行う
- 弱点単元, 誤答パターン, 宿題の重さの適正を出す
- 教材カタログから問題番号レベルの宿題を提案する

#### UC-04. 講師が宿題を承認する

- 講師は提案された宿題を確認する
- 問題を削除, 再提案, 難易度軽減ができる
- 承認後, 生徒向けに宿題を表示する

## 10. データ要件

### 10.1 生徒データ

デモ用に 6人分の架空データを用意する. 最低限の属性は以下.

- `student_id`
- `display_name`
- `grade`
- `target_level`
- `persona_summary`
- `recent_scores`
- `homework_style_notes`
- `weakness_history`
- `preferred_difficulty`

### 10.2 答案データ

各生徒につき少なくとも 1セット以上の答案画像を持つ. できれば以下のパターンを含む.

- ほぼ満点だが一部に思考の癖がある
- 努力しているが途中式が崩れる
- 丸付けはあるが解き直しが不十分
- 宿題量が重すぎると失速する
- 基礎が弱く, 応用に行く前に復習が必要
- 見直し不足でケアレスミスが多い

### 10.3 教材カタログ

教材はデモ用の静的データとして持つ. 1教材でよい. 問題番号レベル提案に必要な最低限の項目は以下.

- `catalog_id`
- `textbook_name`
- `unit_name`
- `chapter_name`
- `problem_no`
- `difficulty`
- `skills`
- `prerequisites`
- `estimated_minutes`
- `tags`

MATH-500 日本語版の翻訳問題など, 利用可能なオープンな問題群を教材風に整形してもよい. ただし, デモ品質を優先し, 問題番号体系を安定化させること.

### 10.4 OCR 中間 JSON

OCR 結果は LLM に直接丸投げせず, 正規化してから渡す. JSON 仕様の最小例は以下.

```json
{
  "student_id": "s-03",
  "source_image_id": "img-20260316-001",
  "page_type": "worksheet",
  "ocr_confidence_summary": {
    "low_confidence_count": 2,
    "notes": ["Q3 の符号が不確実", "Q5 の数字が判読困難"]
  },
  "items": [
    {
      "problem_no": "Q1",
      "recognized_answer": "x=3",
      "teacher_marks": ["circle"],
      "rewrite_detected": false,
      "scratch_notes": "途中式は短い",
      "raw_text": "x=3"
    }
  ]
}
```

### 10.5 分析 JSON

LLM の出力は必ず JSON スキーマ準拠にする. 最小例は以下.

```json
{
  "weak_units": ["一次方程式の移項", "符号処理"],
  "error_patterns": ["分配後の符号ミス", "検算不足"],
  "homework_load_fit": "light",
  "analysis_rationale": [
    "Q3 と Q5 で符号反転ミスが反復している",
    "丸付け後の解き直し痕跡が薄い"
  ],
  "recommended_homework": [
    {
      "problem_no": "A-12",
      "reason": "符号処理の基礎確認",
      "difficulty": "basic"
    }
  ],
  "teacher_note": "次回授業の冒頭で分配法則の確認を3分入れる"
}
```

## 11. OCR 要件

### 11.1 採用方針

第一候補は Azure Vision Read OCR とする. これは作成済みで最小疎通済みであり, デモまでの時間を考えると最も安全である.

### 11.2 OCR の期待値

OCR に過剰な期待をしない. MVP における OCR の役割は次である.

- 文字列候補を抽出する
- 問題番号の対応付け候補を出す
- 低信頼箇所を講師に見せる

### 11.3 OCR の限界前提

以下は OCR 単独では不安定である可能性が高いので, 必ず UI と後段処理で吸収する.

- 丸付け記号の厳密解釈
- 解き直し痕跡の厳密判定
- 手書き数式の意味理解
- 途中式の意図推定

## 12. LLM 要件

### 12.1 採用方針

本線は既存 Azure OpenAI の `gpt-4o-mini` とする. 既存 deployment の API 応答が確認済みであり, Foundry や Marketplace を新規採用するより安全である.

### 12.2 プロンプト方針

LLM には次を厳守させる.

- 必ず JSON で返す
- 教材カタログに存在する問題番号しか提案しない
- OCR で不確実な箇所は過剰断定しない
- 強い断言より仮説として表現する
- 宿題の重さを 軽い / 適正 / 重い のいずれかで必ず出す
- 次回授業への短い講師メモを添える

### 12.3 モデル切替可能性

将来的な比較用に, Hugging Face CLI を用いてオープンモデルを取得し, 別環境で評価する余地を残す. ただし, 本番デモ経路には必須化しない. 本番の安定経路は AOAI を維持する.

## 13. 推論パイプライン要件

```text
画像入力
 -> 画像前処理
 -> Azure Vision OCR
 -> OCR 正規化
 -> 低信頼箇所ハイライト
 -> LLM 分析
 -> 宿題候補生成
 -> 講師承認
 -> 結果保存
```

### 13.1 画像前処理

最低限の前処理を用意する.

- 回転補正
- リサイズ
- コントラスト調整, 任意
- 画像サイズ上限制御

### 13.2 OCR 正規化

最低限の処理を用意する.

- 問題番号の正規化
- 数字, 記号の簡易正規化
- 行単位結果から問題単位へ再構成
- 低信頼箇所の抽出

### 13.3 宿題生成ロジック

宿題は LLM 任せにしすぎない. ルールベースを併用する.

- 教材カタログの problem_no 以外は採用しない
- prerequisite を満たさない問題は除外する
- 推定負荷が重すぎる組合せは避ける
- 似たスキルばかりの重複提案を避ける
- 3〜5問程度を標準とする

## 16. デモデータ要件

### 16.1 架空生徒 6人

少なくとも次のような差を持たせる.

- 努力型だが伸び悩む
- 基礎不足型
- ケアレスミス型
- 宿題負荷過多型
- 解き直し不足型
- 安定高得点だが一部に偏りあり

### 16.2 架空答案

各生徒に対して, 次の観点がデモで見える答案を作る.

- 問題番号が読み取れる
- 途中式がある
- 丸付けがあるものとないものがある
- 解き直しがあるものとないものがある
- 人間が見ても弱点パターンを説明しやすい

### 16.3 教材カタログ

デモで使う教材は 1教材に絞る. 単元, 問題番号, 難易度, 所要時間が揃っていることを重視する.

## 17. エラー処理要件

最低限次を実装する.

- OCR API タイムアウト時の再試行
- LLM API 失敗時の再試行
- JSON パース失敗時のリカバリ
- 画像アップロード失敗時の再送
- ネットワーク不良時のユーザー向けメッセージ

### 17.1 フェイルセーフ

- OCR が崩れた場合でも, 最低限の OCR プレビュー画面へ戻せること
- LLM 分析に失敗した場合でも, OCR 結果だけ表示して手動メモ入力に落とせること
- 宿題提案に失敗した場合でも, 教材カタログから講師が選べる簡易 fallback を用意できるとなおよい

## 18. セキュリティと秘密情報要件

- シークレットは `.env` または安全なシークレット管理に置く
- シークレットをログ出力しない
- 画像や OCR 結果を不要に永続保存しない
- デモデータは架空データのみ使う
- Azure の既存リソースを壊す操作は禁止
- 勝手な Marketplace 契約や Pay-As-You-Go 変更は禁止

## 19. 評価要件, 最重要

この節は Codex の自律ループの中心である. 実装のたびに以下の評価を回し, 合格しない限り完了扱いにしない.

### 19.1 評価原則

- 実装したら必ずテストする
- テストしたら必ず結果を記録する
- 落ちたら原因を分類する
- 原因ごとに改善を入れる
- 改善後に同じ評価を再実行する
- 「動いた気がする」で終わらない

### 19.2 完了判定の4本柱

#### A. デモ成立性

次の happy path が最初から最後まで通ること.

1. 生徒を選ぶ
2. iPad 相当画面で答案画像をアップロードする
3. OCR 結果が表示される
4. 分析結果が返る
5. 宿題候補が返る
6. 講師が承認できる

合格条件:

- 連続 5回実行して 5回とも成功
- 1回でも手動サーバー再起動やキャッシュクリアが必要なら未達

#### B. 応答安定性

デモ用データセットに対し, 以下を満たすこと.

- 画像アップロードから OCR プレビュー表示まで, p95 で 8秒以内
- OCR プレビュー表示から最終分析表示まで, p95 で 12秒以内
- 合計体験時間, p95 で 20秒以内

ネットワークや Azure 側遅延で一時的に超える場合があるので, ローカルでは中央値も記録する. ただし, 20秒を大きく超える構成はデモ不適とみなす.

#### C. 構造化出力信頼性

- LLM の出力 JSON schema 準拠率 100%
- 提案問題番号の教材カタログ存在率 100%
- `homework_load_fit` の空欄率 0%
- 分析理由 `analysis_rationale` の空配列率 0%

ここは絶対条件. 1件でも崩れたら, JSON repair, function calling, schema validation, retry を入れて修正する.

#### D. 講師修正可能性

- 講師が 1問以上削除できる
- 1クリックで再提案できる
- 1クリックで軽い宿題セットに切り替えられる, または同等の操作がある

AI が完璧でなくても現場で使えることを示すため, この条件は必須とする.

### 19.3 OCR 評価要件

デモ用ゴールデンデータを用意し, 少なくとも次を測る.

- 問題番号対応の正答率
- 回答文字列の抽出率
- 低信頼箇所の検出妥当性
- 画像前処理あり / なしでの差分

合格ライン:

- 問題番号対応正答率 95%以上
- 回答文字列の人手確認での実用抽出率 85%以上
- 低信頼箇所での要修正喚起が 70%以上のケースで妥当

注意として, これは教育研究の厳密指標ではなくデモ成立性の指標である. 未達なら, OCR 修正 UI を強化して吸収してよい.

### 19.4 LLM 分析評価要件

6人分以上のデモ生徒に対して, 各1〜2件以上のゴールデンケースを作り, 人手期待値と比較する.

評価項目:

- 弱点単元が期待と大きく外れていないか
- 誤答パターンが答案上の事実から説明可能か
- 宿題の重さがペルソナに合っているか
- 宿題問題番号が教材カタログ内にあり, 意図に合うか
- 講師メモが短く有用か

合格ライン:

- 弱点単元の大筋一致率 80%以上
- 誤答パターンの大筋一致率 80%以上
- 宿題重さの妥当率 85%以上
- 問題番号候補の講師主観受容率 80%以上

ここでの一致率は, 完全一致ではなく「人間がその提案を採用してよいと思えるか」の評価でよい.

### 19.5 UI 評価要件

- iPad 相当の viewport で主要画面が崩れない
- 撮影から承認まで, 説明なしでも 3タップ前後で主要操作に到達できる
- 宿題承認画面で, 提案理由が一目で分かる
- デモ時に文字が小さすぎない

合格ライン:

- 主要3画面でレスポンシブ崩れ 0件
- 想定フローの操作完了が 30秒以内
- デモ観客向けに, 遠目でも主結果が読める

### 19.6 障害注入評価要件

最低限, 次の失敗注入を行う.

- OCR API 1回失敗
- LLM API 1回失敗
- OCR 結果 JSON 欠損
- 画像サイズ過大

合格ライン:

- 失敗理由が画面に分かる
- 再試行導線がある
- アプリ全体が固まらない

### 19.7 デモ体験評価要件

審査で最も重要なので, 実装評価とは別に体験評価を必須にする.

確認項目:

- 10秒で価値が伝わるか
- 「答案を撮るだけで宿題が出る」瞬間があるか
- 6人のばらつきが一目で伝わるか
- 個人情報配慮と edge らしさの説明が自然か
- 「教師を置き換える」ではなく「教師を強くする」メッセージになっているか

合格ライン:

- 第三者 2人以上に見せて, 10秒以内に価値を説明できる
- 第三者 2人以上に見せて, 主機能を1文で言い直してもらい, 趣旨が一致する

## 20. Codex の自律実装ループ要件

Codex は次のループを, 小さく, 何度でも回すこと.

### 20.1 ループ手順

1. 今回の最小目標を1つ決める
2. 変更範囲を限定して実装する
3. 自動テストと手動確認を走らせる
4. 結果を記録する
5. 失敗を分類する
6. 最も効果の高い修正を1つ入れる
7. 再評価する

### 20.2 各ループで必ず残すもの

- 何を直したか
- 何を確認したか
- 何がまだ未達か
- 次に何を直すか

### 20.3 禁止事項

- 巨大な一括実装を先にやる
- テストなしで UI だけ整える
- Azure 側の制約を無視して Foundry や GPU VM に逃げる
- JSON schema が崩れているのに後回しにする
- 「多分大丈夫」で進める

### 20.4 推奨ループ順序

1. 静的データで UI だけ通す
2. OCR API をつなぐ
3. OCR 正規化を固める
4. LLM をつなぐ
5. 宿題提案のルール制約を固める
6. 承認 UI をつなぐ
7. エラー系を入れる
8. デモ演出を磨く

## 21. テスト要件

### 21.1 単体テスト

最低限次を対象にする.

- OCR 正規化関数
- 教材フィルタリング
- 宿題負荷計算
- LLM 出力 schema validation
- API request / response validation

### 21.2 統合テスト

- 画像入力から OCR まで
- OCR JSON から LLM まで
- LLM 出力から承認 UI まで
- happy path end-to-end

### 21.3 スナップショット / ゴールデンテスト

- 6人分の分析 JSON を固定ケースで比較する
- 主要 UI のスクリーンショット差分を確認する

### 21.4 手動テスト

- iPad 相当 viewport
- 低速回線想定
- OCR 失敗ケース
- 宿題再提案ケース

## 22. ログと可観測性要件

最低限次を残す.

- OCR 実行時間
- LLM 実行時間
- 各 retry 回数
- schema validation 成否
- 宿題承認有無

秘密情報と生画像は原則ログに出さない.

## 23. デモ運用要件

### 23.1 デモ当日運用

- 主要データはローカルに事前配置する
- Azure のキー疎通は事前確認する
- 画像は重すぎないサイズにしておく
- 代表ケース 2本をすぐ再演できるようにする
- ネットワーク不調時の fallback 台本を用意する

### 23.2 デモストーリー

1. 教室には6人の生徒がいて, ばらつきが大きい
2. 講師は授業前20分で個別分析が難しい
3. 生徒が iPad で答案を撮る
4. システムが弱点と宿題を出す
5. 講師が承認し, 個別最適な宿題を出せる

## 24. 実装上の明示的な制約

- 既存 Azure OpenAI を本線で再利用する
- Azure AI Foundry を新規本線採用しない
- Marketplace 契約に依存しない
- GPU VM を作らない
- 不要な Azure リソースを増やさない
- 実データではなく架空データを使う
- デモ成立性を研究的厳密性より優先する
